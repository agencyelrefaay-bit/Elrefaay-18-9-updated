# دليل الاختبار الشامل — نظام نجف وإضاءة ERP

الهدف من هذا الملف: تتأكد بنفسك، خطوة بخطوة، إن كل حاجة اتعملت في كل
المراحل (الأمان، QA، الأداء، النشر، النسخ الاحتياطي، PWA) شغالة فعليًا
عندك، مش بس "كلام" في تقرير. كل قسم فيه خطوات + أمر تنفّذه + النتيجة
المتوقعة بالظبط.

> 💡 نصيحة: اختبر الأول على نسخة تجريبية (قاعدة بيانات تجريبية أو نسخة
> محلية)، مش على قاعدة البيانات الحقيقية اللي فيها بيانات العملاء، لحد ما
> تتأكد من كل حاجة.

---

## 0. التجهيز قبل الاختبار

```bash
cd najaf-erp-backend
npm install
cp .env.example .env
```

افتح `.env` واملأ:
```
DATABASE_URL=<قاعدة بيانات تجريبية — Supabase جديد أو Postgres محلي>
JWT_SECRET=<ولّده بـ: node -e "console.log(require('crypto').randomBytes(48).toString('hex'))">
```

```bash
npm run dev
```

**النتيجة المتوقعة:** رسائل نجاح خضراء تنتهي بـ:
```
✓ السيرفر يعمل على المنفذ 5000
```
لو ظهر أي خطأ هنا، شوف `docs/TROUBLESHOOTING.md` قبل ما تكمل.

## 1. اختبار الأمان (Phase 1)

### 1.1 السيرفر يرفض يشتغل من غير JWT_SECRET صحيح
```bash
# احذف JWT_SECRET من .env مؤقتًا أو خليه قصير، وشغّل:
npm run dev
```
✅ **المتوقع:** السيرفر يرفض الإقلاع برسالة `JWT_SECRET غير معرّف أو قصير جداً`
🔧 رجّع الـ `JWT_SECRET` الصحيح بعد الاختبار ده.

### 1.2 تسجيل الدخول وحماية الـ endpoints
```bash
# محاولة وصول من غير توكن — لازم يترفض
curl -i http://localhost:5000/api/products
```
✅ **المتوقع:** `401 Unauthorized`

```bash
# تسجيل دخول صحيح
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```
✅ **المتوقع:** يرجع `token` و`user`. **لازم تغيّر الباسورد ده فورًا من التطبيق بعد أول دخول.**

### 1.3 Rate limiting على تسجيل الدخول
```bash
for i in {1..12}; do
  curl -s -o /dev/null -w "محاولة $i -> [%{http_code}]\n" \
    -X POST http://localhost:5000/api/auth/login \
    -H "Content-Type: application/json" \
    -d '{"username":"admin","password":"wrong"}'
done
```
✅ **المتوقع:** أول 10 محاولات `401`، والمحاولتين 11 و12 `429` (تم تجاوز الحد)

### 1.4 محاولات الدخول الفاشلة بتتسجل في سجل التدقيق
افتح قاعدة البيانات (psql أو Supabase Table Editor) ونفّذ:
```sql
SELECT action, count(*) FROM audit_log WHERE action='login_failed' GROUP BY action;
```
✅ **المتوقع:** رقم أكبر من صفر بعد المحاولات الفاشلة اللي عملتها فوق

## 2. اختبار سيناريوهات العمل الكاملة (Phase 2 — QA)

اعمل التسلسل ده بالظبط من واجهة النظام نفسها (مش API مباشرة) عشان تتأكد
من تجربة المستخدم الكاملة:

| # | الخطوة | النتيجة المتوقعة |
|---|---|---|
| 1 | أنشئ منتج جديد بكمية أولية 0 | يظهر في قائمة المنتجات بباركود تلقائي |
| 2 | أنشئ أمر شراء لنفس المنتج (10 قطع) | يظهر بحالة "مسودة" |
| 3 | حوّل حالة الأمر لـ "مرسل" | الحالة تتغيّر، مينفعش تستلم بضاعة على أمر لسه مسودة |
| 4 | سجّل إيصال استلام جزئي (6 من 10) | المخزون يزيد بـ6 فورًا، الأمر يبقى "استلام جزئي" |
| 5 | **حاول تستلم 6 قطع تانية على نفس البند** | ❌ **لازم يترفض** برسالة "الكمية تتجاوز المتبقي" — ده بالظبط الباج اللي اتصلح |
| 6 | أنشئ فاتورة مبيعات (2 قطعة من نفس المنتج) | تظهر كمسودة، المخزون لسه ملوش تأثير |
| 7 | أكّد الفاتورة | المخزون ينقص بـ2 فورًا |
| 8 | **حاول تأكد نفس الفاتورة تاني (double-click أو زرار تأكيد مرتين)** | ❌ **لازم يترفض** برسالة "تم تأكيدها بالفعل" — ده الباج التاني اللي اتصلح |
| 9 | سجّل مرتجع على الفاتورة (قطعة واحدة) | يظهر بحالة "قيد الانتظار" |
| 10 | اعتمد المرتجع | المخزون يرجع يزيد بقطعة واحدة |
| 11 | سجّل دفعة عميل جزئية | رصيد العميل يتحدث في تقرير الأرصدة |
| 12 | افتح تقرير لوحة التحكم | صافي الربح يظهر صحيح (سعر البيع − سعر التكلفة × الكمية المباعة) |

✅ **لو كل صف طلع بالنتيجة المتوقعة بالظبط (خصوصًا الصفوف 5 و8)، يبقى إصلاحات الـ race conditions شغالة.**

## 3. اختبار الأداء (Phase 3)

### 3.1 التأكد إن الفهارس الجديدة اتعملت فعليًا
```sql
\di idx_invoice_items_invoice idx_cust_inst_invoice idx_audit_log_user
```
✅ **المتوقع:** 3 صفوف تظهر (الفهارس موجودة)

### 3.2 التأكد إن الفهرس بيتستخدم فعليًا (مش بس موجود)
```sql
EXPLAIN SELECT * FROM invoice_items WHERE invoice_id = 1;
```
✅ **المتوقع:** السطر يحتوي على `Index Scan` أو `Bitmap Index Scan` على `idx_invoice_items_invoice` (مش `Seq Scan`)

### 3.3 سرعة تقرير الأرصدة
```bash
TOKEN="<حط التوكن بتاعك هنا>"
curl -s -o /dev/null -w "الوقت: %{time_total}s\n" \
  -H "Authorization: Bearer $TOKEN" http://localhost:5000/api/reports/balances
```
✅ **المتوقع:** أقل من ثانية حتى مع مئات العملاء/الموردين

## 5. اختبار النشر (Phase 5)

### 5.1 Docker (لو عندك Docker مثبت)
```bash
docker build -t najaf-erp .
docker run --rm -p 5000:5000 --env-file .env najaf-erp
```
✅ **المتوقع:** الصورة تتبني بنجاح، والكونتينر يقلع ويطبع نفس رسائل النجاح

```bash
curl http://localhost:5000/api/health
```
✅ **المتوقع:** نفس نتيجة 4.1

### 5.2 docker-compose (على VPS)
```bash
docker compose up -d --build
docker compose logs -f app
```
✅ **المتوقع:** healthcheck يتحول لـ "healthy" خلال ثواني

### 5.3 Railway
- ادفع الكود لـ Railway (أو اربط الـ repo)
- اضبط متغيرات البيئة من `.env.example`
- ✅ **المتوقع:** الـ deploy ينجح، و`/api/health` يرجع 200 من رابط Railway

⚠️ **الأهم:** اختبر النشر على قاعدة بيانات **فاضية تمامًا** (مشروع Supabase جديد) مرة على الأقل — ده كان فيه باج حرج قبل كده (ترتيب migrations) اتصلح، ولازم تتأكد إنه شغال عندك.

## 6. اختبار النسخ الاحتياطي (Phase 6 — Backups)

```bash
sudo apt install -y postgresql-client   # لو مش مثبت
bash deploy/backup.sh
```
✅ **المتوقع:** ملفين جوه `backups/`: `db_<تاريخ>.sql.gz` و`uploads_<تاريخ>.tar.gz`، وسطر أخير "اكتمل النسخ الاحتياطي بنجاح"

```bash
# تحقق من محتوى النسخة
zcat backups/db_*.sql.gz | head -20
```
✅ **المتوقع:** أوامر SQL حقيقية (مش ملف فاضي)

### اختبار الاستعادة (⚠️ على قاعدة بيانات تجريبية بس، مش الحقيقية)
```bash
bash deploy/restore.sh backups/db_<التاريخ>.sql.gz
```
✅ **المتوقع:** يطلب تأكيد صريح (`yes`) قبل ما يعمل أي حاجة

## 7. اختبار PWA (Phase 6 — Desktop Experience)

### 7.1 على الكمبيوتر (Chrome أو Edge فقط)
1. افتح رابط النظام
2. ✅ **المتوقع:** بعد ثواني، زرار ذهبي "تثبيت التطبيق" يظهر أسفل الشاشة، أو أيقونة ⊕ في شريط العنوان
3. اضغط تثبيت
4. ✅ **المتوقع:**
   - اختصار يظهر على سطح المكتب
   - مدخل يظهر في قائمة Start
   - التطبيق يفتح في نافذة مستقلة **بدون** شريط عنوان المتصفح أو تابات

### 7.2 على Android (Chrome)
1. افتح الرابط
2. ✅ **المتوقع:** إشعار "إضافة إلى الشاشة الرئيسية" يظهر تلقائيًا (أو من قائمة ⋮)
3. ثبّت التطبيق
4. ✅ **المتوقع:** أيقونة على الشاشة الرئيسية + splash screen بألوان النظام عند الفتح + بدون شريط عنوان

### 7.3 اختبار الأوفلاين
1. افتح التطبيق (وهو متصل بالنت) مرة واحدة على الأقل
2. اقطع الإنترنت بالكامل
3. أعد فتح التطبيق
✅ **المتوقع:** الواجهة تفتح (مش شاشة بيضاء)، وأي محاولة تحميل بيانات (منتجات، فواتير) تظهر رسالة واضحة إنك محتاج اتصال — **مفيش بيانات قديمة مضلِّلة بتتعرض وكأنها حديثة**

### 7.4 اختبار التحديث
1. غيّر `CACHE_VERSION` في `public/sw.js` من `v1` لـ `v2`
2. انشر النسخة الجديدة
3. افتح التطبيق المُثبَّت مسبقًا عند المستخدم
✅ **المتوقع:** خلال دقائق (أو بعد إعادة فتح التطبيق)، شريط أعلى الشاشة يظهر "📦 يتوفر تحديث جديد" — اضغط "تحديث الآن" ويشتغل بالنسخة الجديدة

### 7.5 فحص فني إضافي (اختياري، لو حابب تتأكد بعمق)
افتح Chrome DevTools (F12) → تبويب **Application**:
- ✅ **Manifest:** يظهر بدون أخطاء حمراء، مع كل الأيقونات ظاهرة
- ✅ **Service Workers:** حالة "activated and is running"
- ✅ **Cache Storage:** كاش باسم `erp-shell-v1` فيه ملفات الواجهة والأيقونات — **وبدون أي مفتاح فيه `/api/`**
