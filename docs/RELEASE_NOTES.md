# سجل التغييرات — Stage 5: التجهيز للإنتاج

مراجعة وتجهيز إنتاجي شامل تم على النظام (المراحل 1–4 كانت جاهزة ومستقرة
ومتفترض إنها شغالة صح — لم يُعاد بناء أي منها، فقط إصلاحات مستهدفة).

## 🔒 الأمان

- إزالة fallback ثابت لـ `JWT_SECRET` في الكود — السيرفر يرفض يشتغل من
  غير مفتاح حقيقي بطول 32+ حرف (كان في السابق ممكن يشتغل بمفتاح معروف
  للعامة لو حد نسي الـ env var)
- إضافة rate limiting: حد عام على `/api` (600 طلب/15 دقيقة) وحد صارم على
  تسجيل الدخول (10 محاولات/15 دقيقة) لمنع هجمات brute-force
- إضافة `helmet` لـ security headers الأساسية
- تسجيل محاولات الدخول الفاشلة في سجل التدقيق (audit log)
- CORS قابل للتقييد عبر `ALLOWED_ORIGINS` (اختياري، مفيش تغيير في
  السلوك الافتراضي)
- **⚠️ إجراء مطلوب منك:** ملف `.env` المرفوع فيه سبق وكان يحتوي بيانات
  إنتاج حقيقية مكشوفة — لازم rotation فوري لـ `DATABASE_URL` و`JWT_SECRET`
  و`TELEGRAM_BOT_TOKEN`

## 🐛 إصلاحات Race Conditions (بيانات مالية/مخزون)

- **تأكيد فاتورة مزدوج:** طلبين "تأكيد" متزامنين لنفس الفاتورة كانوا
  ممكن يخصموا المخزون مرتين ويولّدوا عمولة مكررة — تم قفل صف الفاتورة
  (`FOR UPDATE`) وإعادة التحقق من الحالة داخل المعاملة
- **استلام أكبر من المطلوب:** إيصالي استلام متزامنين لنفس بند أمر شراء
  كانوا ممكن يستلموا كمية إجمالية أكبر من المطلوب فعلياً — تم قفل بند
  أمر الشراء وإعادة التحقق من الكمية المتبقية داخل المعاملة

## ⚡ الأداء

- 14 index جديد على أعمدة foreign key كانت بتتفلتر/تتربط عليها كتير
  بدون index (أهمها `invoice_items.invoice_id`) — بيتنفذوا تلقائياً عند
  إقلاع السيرفر
- إصلاح N+1 في `/api/reports/balances`: تحديد أقصى تزامن (6) بدل إطلاق
  استعلامات بلا حدود لكل مورد/عميل، لتفادي استنزاف connection pool مع
  نمو عدد العملاء/الموردين

## 📋 Production Polish / Logging

- Logger مهيكل (JSON) بدل console.error خام — بيسجل السياق الكامل
  (المسار، المستخدم، الحالة) مع كل خطأ
- إضافة `process.on('uncaughtException'/'unhandledRejection')` — كانت
  مفقودة تماماً، فأي خطأ غير متوقع خارج نطاق طلب HTTP كان بيمر بصمت
- `/api/health` بقى بيتحقق فعلياً من الاتصال بقاعدة البيانات (503 لو
  مقطوعة) بدل ما يرجع "ok" ثابت دايماً

## ما لم يتم تغييره عمداً

- منطق الأعمال في `installmentEngine.js`, `commissionEngine.js`,
  دفاتر الأستاذ — روجعت ووجدت سليمة، لم تُلمس تفادياً لأي مخاطرة غير
  ضرورية على حسابات مالية شغالة ومستقرة
- ثغرة `xlsx` (SheetJS) — high severity بدون إصلاح متاح من المصدر.
  الاستخدام داخلي فقط (مستخدمين مسجلين دخول برتبة admin/warehouse)، مش
  endpoint عام، فالمخاطرة الفعلية محدودة. موصى بيه كمتابعة لاحقة: تقييم
  الانتقال لـ `exceljs` أو مراجعة الحاجة الفعلية لاستمرار استخدام الحزمة

## 🔴 تدقيق قبول نهائي (Final Acceptance Audit) — الجولة الثانية

تدقيق شامل ثاني بعد التسليم الأول، شمل تشغيل فعلي حقيقي (مش قراءة كود
بس): تركيب PostgreSQL محلي، تشغيل السيرفر ضد قاعدة بيانات فاضية تمامًا،
واختبار UAT كامل عبر الـ API الحقيقي.

### 🔴 Bug حرج جديد — اكتُشف فقط بالتشغيل الفعلي، لم يظهر بمراجعة الكود

**ترتيب migrations خاطئ يمنع أي تركيب جديد من الإقلاع نهائيًا.**
3 دوال migration (`migrateCollectionSchema`, `migrateNotificationsSchema`,
`migrateReturnsSchema`) كانت بتتنفذ *قبل* الدوال اللي بتنشئ الجداول اللي
هي بتعتمد عليها (`customers`, `settings`, `customer_payments`,
`sales_returns` — كلهم جوه `createSalesSchema`/`createPhase4Schema`).
كان شغال على السيرفر الحالي بالصدفة بس لأن الجداول دي كانت موجودة بالفعل
من تراكم نشرات سابقة. **أي عميل جديد أو بيئة Railway/VPS جديدة كان
السيرفر هيفشل في الإقلاع من أول تشغيل.** تم اكتشافه بتشغيل السيرفر فعليًا
ضد قاعدة بيانات PostgreSQL فاضية تمامًا (مش SQLite قديم، مش قاعدة بيانات
فيها بيانات من قبل)، وتم إصلاحه بإعادة ترتيب الاستدعاءات في `server.js`
والتحقق مرة تانية بتشغيل ناجح كامل. **هذا كان أخطر باج في التسليم كله.**

### ✅ UAT فعلي — تم تنفيذه بالكامل (مش محاكاة)

اتعمل عبر HTTP requests حقيقية على سيرفر فعلي شغال + قاعدة بيانات
PostgreSQL محلية حقيقية:
تسجيل دخول + رفض توكن مفقود (401) + رفض باسورد غلط (401) → إنشاء منتج
وتصنيف ومورد وعميل → إنشاء أمر شراء → تحويل لحالة "sent" → استلام جزئي
(6 من 10) → التأكد من تحديث المخزون فعليًا (6 وحدات) → **محاولة استلام
زيادة عن المتبقي فعليًا رُفضت بنجاح (تأكيد حي لإصلاح Stage 5 الأول)** →
إنشاء فاتورة مبيعات (مسودة) → تأكيدها → **محاولة تأكيدها مرة ثانية
رُفضت بنجاح (تأكيد حي لإصلاح double-confirm)** → التحقق من خصم المخزون
فعليًا → توليد PDF حقيقي (3 صفحات) → توليد رابط واتساب بتنسيق صحيح →
تسجيل دفعة عميل جزئية → تقرير الأرصدة (يستخدم إصلاح N+1 من Stage 5،
استجابة 7.7ms) → لوحة تحكم KPIs (صافي ربح صحيح: 600 = 1600 إيراد − 1000
تكلفة) → مرتجع مبيعات كامل (pending → موافقة → إتمام) مع تأكيد رجوع
المخزون فعليًا → دفعة مورد → تحميل قالب استيراد Excel حقيقي → إنشاء
مستخدم بدور "sales" واختبار حدود الصلاحيات فعليًا (403 على `/users`
و`/reports`، 201 على إنشاء فاتورة) → التأكد من تسجيل محاولة الدخول
الفاشلة في `audit_log` فعليًا → **التأكد بـ `EXPLAIN` إن
`idx_invoice_items_invoice` (من إصلاح الأداء) بيتستخدم فعليًا من الـ
query planner**.

### ⚠️ تم بصدق — لم يُنفَّذ فعليًا (قيود بيئة هذا التسليم)

- **`docker build` الفعلي:** بيئة التدقيق دي معندهاش Docker daemon.
  `Dockerfile` اتحقق منه بديل عبر تنفيذ نفس أوامره يدويًا (`npm ci
  --omit=dev` نجح)، لكن الـ build الكامل للصورة لازم يتنفذ على جهازك/
  سيرفرك قبل الاعتماد الكامل عليه.
- **UAT على واجهة المستخدم الفعلية (المتصفح):** الاختبار تم على مستوى
  الـ API مباشرة (HTTP requests)، مش click-through فعلي على الفرونت اند
  في متصفح حقيقي. الفحص اللي تم على الفرونت اند (تحت) هو static
  analysis للكود، مش تشغيل تفاعلي.

## 🖥️ Phase 6 — Desktop Experience & PWA

النظام دلوقتي Progressive Web App كامل، قابل للتثبيت على Windows
(Chrome/Edge) وAndroid، بيفتح كتطبيق مستقل بدون شريط عنوان المتصفح.

### الملفات الجديدة
- `public/manifest.json` — هوية التطبيق (اسم، أيقونات، ألوان، shortcuts)
- `public/sw.js` — Service Worker بإستراتيجية تخزين مؤقت آمنة للـ ERP
- `public/offline.html` — صفحة احتياطية عند انقطاع الإنترنت
- `public/icons/` — طقم أيقونات كامل (8 مقاسات + نسختين maskable + apple-touch-icon + favicons)، مصممة لتطابق الهوية البصرية الحالية (Obsidian + Burnished Gold)
- `scripts/generate-icons.js` — لإعادة توليد الأيقونات لو الهوية البصرية اتغيّرت مستقبلاً
- `docs/PWA_GUIDE.md` — دليل التثبيت والتحديثات الكامل

### القرار الأهم: لا تخزين مؤقت لأي بيانات API إطلاقًا
كل طلبات `/api/*` بتتحول دايمًا على الشبكة مباشرة، بدون أي قراءة أو كتابة
كاش. هذا قرار متعمد وغير قابل للتفاوض — عرض بيانات مالية/مخزون قديمة
مخزنة محليًا أخطر بكتير من ظهور رسالة "لا يوجد اتصال" وقت انقطاع النت.
اللي بيتخزن مؤقتًا هو الـ app shell فقط (الواجهة نفسها + الأيقونات).

### التحقق الفعلي (مش claim فقط)
- تشغيل السيرفر فعليًا + `curl` مباشر: `manifest.json` (200، JSON صالح،
  كل الحقول المطلوبة موجودة، كل رابط أيقونة فيه بيرجع 200)، `sw.js` (200
  مع `Cache-Control: no-cache` صحيح، syntax صالح)، `offline.html` (200)،
  كل الأيقونات (200)
- تأكيد إن `index.html` فعليًا بيحمّل الـ manifest ويسجّل الـ service worker
- **Regression check:** تسجيل دخول + قوائم منتجات/فواتير + تقرير KPIs
  اتأكدوا شغالين 200 بعد كل تعديلات الـ PWA — مفيش أي تأثير على منطق
  العمل الأساسي

### ⚠️ لم يُختبر فعليًا (قيود بيئة هذا التسليم)
- **التثبيت الفعلي على Windows/Android عبر متصفح حقيقي:** بيئة التدقيق
  هنا سيرفر بدون واجهة رسومية أو متصفح Chrome/Edge حقيقي، فمعندهاش طريقة
  أشغّل بيها `beforeinstallprompt` الفعلي أو أتأكد بصريًا من ظهور اختصار
  سطح المكتب. كل الملفات مبنية طبق المواصفة الرسمية لـ PWA (manifest
  schema صحيح، service worker مسجَّل بشكل صحيح، الشروط التقنية للتثبيت
  كلها متوفرة)، لكن **التحقق البصري النهائي على جهاز Windows/Android حقيقي
  لازم يتم عندك قبل الاعتماد الكامل**. الخطوات بالتفصيل في
  `docs/PWA_GUIDE.md`.
- Lighthouse PWA audit الرسمي: يحتاج متصفح Chrome حقيقي، غير متاح في بيئة التدقيق
