# دليل النسخ الاحتياطي والاستعادة — نظام نجف وإضاءة ERP

## الاستراتيجية (خطين دفاع، مش خط واحد)

### 1. Supabase — خط الدفاع الأساسي (لو الاستضافة قاعدة البيانات عليه)
Supabase بيوفر نسخ احتياطي تلقائي يومي (وPoint-in-Time Recovery في خطط
Pro فما فوق) بدون أي إعداد إضافي منك. **راجع من Dashboard المشروع:**
Database → Backups، وتأكد إن الخطة اللي مفعّلة عندك فعلاً بتشمل نسخ
احتياطي يومي كافٍ لاحتياجاتك. هذا أهم خط دفاع لأنه خارج أي سيرفر بتشغّله
إنت، ومحصّن من أي مشكلة في الـ VPS/Railway نفسه.

### 2. `deploy/backup.sh` — خط دفاع إضافي (نسخة عندك تحت تحكمك)
سكريبت بياخد نسخة `pg_dump` من قاعدة البيانات + نسخة `tar` من ملفات
uploads (صور المنتجات، إثباتات الدفع)، يضغطهم، ويحذف تلقائياً أي نسخة
أقدم من 14 يوم (قابل للتغيير). مفيد في حالات: احتياج نسخة محلية سريعة،
نقل لسيرفر جديد، أو لو خطة Supabase عندك ماعندهاش Point-in-Time Recovery.

**متطلبات:** `pg_dump` و`psql` مثبتين على السيرفر (مش جوه كونتينر Docker
التطبيق — السكريبت مصمم يشتغل على الـ VPS host نفسه):
```bash
sudo apt update && sudo apt install -y postgresql-client
```

## التشغيل اليدوي
```bash
cd /path/to/najaf-erp-backend
bash deploy/backup.sh
```
هيطلع لك ملفين جوه `backups/`: `db_<تاريخ-ووقت>.sql.gz` و`uploads_<تاريخ-ووقت>.tar.gz`

## الجدولة التلقائية اليومية (VPS عبر cron)
```bash
crontab -e
# أضف السطر ده (نسخة كل يوم الساعة 3 صباحاً):
0 3 * * * cd /path/to/najaf-erp-backend && bash deploy/backup.sh >> logs/backup.log 2>&1
```

## Railway
الملفات جوه كونتينر Railway بتتمسح مع كل redeploy (ephemeral filesystem)،
فـ `backup.sh` مش مناسب يتشغل هناك مباشرة. الاعتماد الأساسي على Railway
لازم يكون Supabase backups (فوق). لو محتاج نسخة إضافية من Railway نفسه،
الخيار الأنسب هو Railway Cron Job منفصل (service صغير بيشغّل نفس منطق
`pg_dump` على معاد ثابت) بيرفع الناتج لتخزين خارجي (S3/Backblaze B2) —
ده قرار بنية تحتية إضافي حسب احتياجك الفعلي، مش جزء من هذا التسليم.

## التحقق من نجاح النسخة الاحتياطية
```bash
# افتح أول كذا سطر من ملف قاعدة البيانات المضغوط للتأكد إنه SQL حقيقي مش فاضي
zcat backups/db_<التاريخ>.sql.gz | head -20
```
السكريبت بيرفض يكمل ويبعت تنبيه لو الملف الناتج فاضي (شوف `notify_failure`
جوه `backup.sh`) — لو عندك `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` في
`.env` بالفعل، أي فشل في النسخ الاحتياطي هيوصلك تنبيه تيليجرام تلقائياً.

## الاستعادة (Restore) — ⚠️ للطوارئ فقط
```bash
bash deploy/restore.sh backups/db_2026-07-15_03-00-00.sql.gz backups/uploads_2026-07-15_03-00-00.tar.gz
```
السكريبت بيوريك قاعدة البيانات المستهدفة (مع إخفاء كلمة المرور) وبيطلب
تأكيد صريح (`yes`) قبل ما يمسح أي حاجة. بعد الاستعادة لازم تعيد تشغيل
السيرفر (`pm2 restart najaf-erp` أو `docker compose restart`).

## نصائح مهمة
- اختبر الاستعادة فعلياً مرة على الأقل على بيئة تجريبية (staging) قبل ما
  تحتاجها فعلياً في كارثة حقيقية — نسخة احتياطية ملهاش قيمة إلا لو أثبتت
  إنها بترجع فعلاً.
- خزّن نسخة من `backups/` بعيد عن نفس السيرفر بشكل دوري (rsync لسيرفر
  تاني، أو رفعها يدوياً/آلياً لتخزين سحابي) — نسخة احتياطية على نفس القرص
  اللي ممكن يتعطل مالهاش قيمة كبيرة وقت الكارثة الفعلية.
